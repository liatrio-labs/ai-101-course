Why it sometimes makes things up
“The capital of France is ”
TRAINING LEARNS WEIGHTS THAT SCORE NEXT TOKENS AT RUNTIME
{{ p.word }}
{{ p.pct }}
At runtime, the model picks a likely token, adds it to the text, and repeats one token at a time.
so what's a hallucination?
The model never knows anything. It only scores. When the pattern is rare, or the window is full of muddled context, the scores still pick a winner, so out comes a confident, fluent, wrong answer.
A model can say “I don't know,” but it does not reliably know when to abstain. Tools, source documents, and a clean context window ground the answer in something real.

When the box fills up: your three options
92% full · 40 turns of chat
slower · pricier · easier to distract
1 · Drop
drop the oldest messages, keep the newest
free and automatic, but early detail is simply gone
2 · Compact
ask the model to summarize the old part, keep the summary
30 turns → one paragraph
keeps the thread; costs one extra call; fine detail gets lost, especially after repeated compactions
3 · Hand Off
new chat, paste back only what matters
cheapest and sharpest; you decide what's worth carrying over
A clean context window that is intentionally constructed beats a big messy one that has evolved over many turns. Everything in the box competes for the model's attention, so irrelevant history actively makes answers worse.
Can it do math? Reliability vs. exact calculation
“1 + 1 = 2”
✓ right, but a correct answer does not prove reliable arithmetic.
“1 + 1 =” is followed by “2” countless times in training text, so “2” is a likely next token. This is pattern completion.
“4,391 × 7,208 = 31,648,528”
✕ a typical wrong answer. The true value is 31,650,328.

Recap: the whole thing in four ideas
The list
A chat is a list of messages. Each turn gets the relevant context, either by resending it or by reusing stored state. That's why it seems to remember.
The box
The context window is a fixed box measured in tokens. Only what's inside exists; the overflow is genuinely gone.
The prediction
It only predicts the next token. Fluent and confident even when wrong, and incapable of native operations outside of text prediction.

A frozen text predictor, handed a list of messages in a fixed box, run in a loop by ordinary software that does all the fetching.
Each piece explains something you'll encounter: confident wrong answers come from the predictor, missing context from information falling out of a box that filled up, and anything it appears to do in the world from the loop calling a tool.

# Monthly report
Always pull figures from the finance sheet, never from chat.
## Steps
1. Check last month's file for the format
2. Fill the four sections in order
3. Flag anything down more than 5%
## Done when
Every number has a source noted beside it.
This is a basic skill: instructions in a Markdown file. A skill can also include scripts, references, and assets. It adds no training or permissions; the host decides discovery and loading.
why bother
The judgment your best people carry in their heads becomes something the whole team can run; reviewable, correctable, and improving with every pass.
and you don't have to write it yourself
Talk through the job once and ask the AI to help you convert it to a skill. Most tools ship a skill for making skills, so your job is reviewing the draft, not authoring it.

The harness: the software wrapped around the model
the harness · the app, running on your side
{{ h.text }}
↕ sends text over the internet, gets text back
outside the harness · someone else's datacenter
the model
frozen · stateless · text in, text out. It does exactly one thing.
why the word matters
Almost everything you think of as “the AI” is the harness, not the model: ChatGPT, Claude.ai, Copilot and Codex are harnesses.
Same model, different harness → very different experience. It explains why one product can browse and another can't, why one remembers your files, and why “the AI can't do X” is usually the harness, not the model.
It's also what manages the context window: trimming, compacting, and choosing what to send are all harness decisions.
Three words people mix up; tools, skills, plugins
a capability
Tool · tool call
A tool is something the harness can do: read a file, search, perform a calculation. A tool call is the model asking for one and getting the result back as text.
gives it new abilities
instructions
Skill
A written playbook for a kind of work: “here's how we build a spreadsheet”. Just text, pulled into the window when it's relevant.
gives it know-how, no new powers
plumbing
Plugin · connector
A package you switch on that hands the harness a bundle of new tools: connect your email, and “search inbox” and “send draft” appear.
delivers more tools
Skills teach · plugins add · tool calls do.
And none of them change the model itself. The model is always based on its own static training data. Tools, Skills, and Plugins change what's in the context window and what the harness can run.
Products name these differently; “actions”, “connectors”, “extensions”, “MCP servers”. Ask which of the three it is and the confusion clears.

This is why “write the spec first” works so well with agents: the spec is a persistent artifact. It survives every trim, and it gives you and the agent one shared definition of “done”.
Rule of thumb: if losing it would hurt, it doesn't belong in the chat; it belongs in a file.
